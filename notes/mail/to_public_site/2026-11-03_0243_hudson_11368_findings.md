# Hudson 11368: the list and the detail read different sources

This answers 2026-11-03_0237_hudson_11368_checked_flag.md.
I have not yet reproduced it in a browser. What follows comes from the code and the file.
I could not read the production database. That read needs Ray's approval.

## 1. What each view reads

- The green checkmark in the list comes from ischecked. The browser computes it and keeps it in memory.
  It is green when checked is 1 and some verify flag is 1.
  It is computed when the job loads, and again after most saves.
  It is never stored in the database.
- The [x] box in the detail view comes from the database record, read fresh each time a ballot opens.
- So yes, they read different fields. They disagree when the in-memory row goes stale.

## 2. How adjudicator.json is built

Save File writes only the rows whose in-memory ischecked is green.
Each row then takes checked, verify and tags from a copy of the database records.
That copy is read when the job loads, or when a filter changes the URL.
A save does not update it.

So the file mixes two moments: ischecked from now, and checked from the last load.
A ballot opened and then marked complete between two loads is written as checked False with ischecked green.
That alone gives the file state you found, even if the database holds checked true.

## 3. A second defect that writes exactly this database state

Several actions start a save that runs 500 ms later.
Marking a contest complete is one of them.
Opening another ballot does not cancel it.
If the reviewer opens the next ballot within 500 ms, the save runs on the new ballot.
It writes the new ballot's state before its record has loaded:

- checked 0
- verify with AuditEngine 1, the default source
- tags as an empty list
- adj_info from the AuditEngine column

That matches 11368 field for field, including the vote for Warren.
It would happen if Ray marked the ballot before 11368 complete and clicked 11368 at once.
I have not yet shown in a test that this also leaves the checkmark green.

## 4. checked 0 in the attrs of adjud_contest_daf

That is normal. AuditEngine writes those attrs, and AdjudiTally never changes them.
It is 0 in all 113 records.

## 5. What would settle it

A read-only query of the audit_adjunction record for 11368: its checked, verify, tags and updated_at.
The updated_at of 11367 and 11369 too.
If 11368 shows checked true, section 2 explains it alone.
If it shows checked false, with updated_at within a second of a neighbor's, section 3 does.

## 6. Proposed fix, for Ray's approval

1. Compute the checkmark from checked and verify in one function, and use it in the list, the detail and the export.
2. After each save, update that ballot's record in the in-memory copy, so the export uses the saved values.
3. Cancel a pending save when another ballot opens. Or tie the save to the ballot it was started for.

All three change behavior, so I will not start until Ray approves.
The data in the job stays as it is.
